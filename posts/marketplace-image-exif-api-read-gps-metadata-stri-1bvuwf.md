# Marketplace Image EXIF API: Read GPS Metadata, Strip It Before Promo Rendering

TL;DR: For a marketplace that turns seller images into short promo videos, decode and re-encode every accepted image at upload, store the sanitized derivative as the only rendering input, and retain the original in separate short-lived quarantine only when an authorized audit requires it. Read metadata on demand from that quarantine copy, never from the public asset path. This makes location removal a boundary invariant instead of a promise that every later video job must remember.

The decision is driven by exposure, not convenience. EXIF can carry GPS coordinates, while an image may also contain metadata outside the EXIF block. Deleting a few GPS keys is therefore a weaker privacy control than producing a fresh, metadata-free derivative. The original may still help a narrowly defined moderation or dispute workflow, but it should not become the source for previews, retries, thumbnails, or downloads.

## Should an image EXIF API read metadata or strip it?

Three invariants define this design. No renderable marketplace object contains inherited metadata. An asynchronous promo-video worker cannot fetch the quarantined original with its normal runtime identity. A retry consumes the same sanitized image and keeps the same privacy posture even if queue delivery is duplicated.

Those rules matter because prompt-to-video work is rarely one request. An upload can fan out into validation, moderation, frame composition, encoding, thumbnail generation, and CDN publication. If stripping happens inside the final render worker, every preview path and future worker becomes another place to make the privacy decision. One forgotten branch is enough.

Retries count.

Be conservative about formats. MDN documents that common web image types have different capabilities and browser support, so acceptance should follow an explicit allowlist rather than a filename suffix. OWASP's file-upload guidance calls for validating the file type, renaming stored files, limiting size, and keeping uploads outside the webroot. Metadata handling belongs inside that hostile-upload boundary; it does not replace content validation.

Fail closed.

A decoder error must reject or quarantine the upload, not fall back to publishing the original. A successful metadata scan followed by a failed re-encode is not partial success. There is no publishable asset until the clean derivative has been written and verified.

## Decision: process at upload, inspect on demand

The useful comparison is not "read versus strip." It is where each operation sits relative to publication.

| Option | Public rendering path | Privacy failure boundary | Operational trade-off | Valid use |
| --- | --- | --- | --- | --- |
| Re-encode at upload; audit the original on demand | Always uses the derivative | Upload transaction | More work before acceptance; simpler workers | Default marketplace path |
| Read and selectively delete fields | Uses a modified source | Parser and metadata-family coverage | Preserves source structure; needs a complete removal policy | Controlled archival workflows |
| Strip inside each video job | Original may cross queues and workers | Every consumer and retry | Faster acceptance; larger authorization surface | Closed systems with non-sensitive originals |
| Inspect only after a complaint | Original remains renderable | Entire pre-complaint lifetime | Minimal ingest work; weak prevention | Forensic collections that are never published |

The first option wins here because a seller's product photo can become several visible artifacts. Paying the decode cost once at ingress keeps privacy behavior independent of how many promo variants are requested later. It also separates two retention clocks: the derivative can live with the listing, while the quarantined original can expire under a shorter policy unless a legitimate case places it on hold. The exact duration is a governance choice, not a magic number.

Consider the failure sequence behind that choice. A seller uploads a portrait-oriented JPEG whose correct display depends on EXIF orientation and whose GPS block identifies the capture location. The first promo render times out after composing frames, so the queue redelivers its job. Meanwhile, a listing preview and a moderation thumbnail are generated by separate consumers. Stripping inside the renderer protects only the completed video; it says nothing about the preview, the moderation copy, the timed-out worker's temporary files, or the retry payload. Re-encoding once at ingress collapses those branches into one decision. The pixels are oriented before metadata disappears, each consumer receives the derivative key, and none needs permission to retrieve the original. This is a clear trade: ingestion performs more work and must handle decoder failure, while every later path becomes smaller and easier to audit.

Reading still has a role. An authorized audit can record whether location-bearing tags were present, which policy decision followed, and which derivative object was produced. Avoid putting raw coordinates into logs, traces, queue payloads, or analytics. A boolean such as `gps_present`, an internal reason code, and a content digest usually answer the operational question without creating a second location database.

## The critical path in Python

This boundary accepts only formats chosen by policy, removes orientation ambiguity by transposing pixels, and saves a new file without passing source metadata to the encoder. Pillow documents both `Image.verify()` and `ImageOps.exif_transpose()`; its handbook also warns about decompression bombs. Storage remains abstract because authorization and atomic publication belong to the surrounding system.

```python
from __future__ import annotations

import hashlib
import io
from dataclasses import dataclass
from typing import BinaryIO, Protocol

from PIL import Image, ImageOps, UnidentifiedImageError

ALLOWED_FORMATS = {"JPEG", "PNG", "WEBP"}
GPS_INFO_TAG = 34853


class PrivateStore(Protocol):
    def put_quarantined(self, digest: str, source: BinaryIO) -> str: ...


class PublicStore(Protocol):
    def put_derivative(self, digest: str, payload: bytes, media_type: str) -> str: ...


@dataclass(frozen=True)
class IngestResult:
    derivative_key: str
    quarantine_key: str
    source_sha256: str
    gps_present: bool


def ingest_image(
    source: BinaryIO, private: PrivateStore, public: PublicStore
) -> IngestResult:
    raw = source.read()
    digest = hashlib.sha256(raw).hexdigest()

    try:
        with Image.open(io.BytesIO(raw)) as probe:
            probe.verify()
        with Image.open(io.BytesIO(raw)) as opened:
            if opened.format not in ALLOWED_FORMATS:
                raise ValueError("unsupported image format")
            gps_present = GPS_INFO_TAG in opened.getexif()
            pixels = ImageOps.exif_transpose(opened).convert("RGB")
    except (Image.DecompressionBombError, UnidentifiedImageError, OSError) as exc:
        raise ValueError("image failed validation") from exc

    clean = io.BytesIO()
    pixels.save(clean, format="JPEG", quality=90, optimize=True)
    quarantine_key = private.put_quarantined(digest, io.BytesIO(raw))
    derivative_key = public.put_derivative(
        digest, clean.getvalue(), "image/jpeg"
    )
    return IngestResult(
        derivative_key=derivative_key,
        quarantine_key=quarantine_key,
        source_sha256=digest,
        gps_present=gps_present,
    )
```

This is a critical path, not a complete upload service. Enforce byte and pixel limits before allocating large buffers, pin and patch the decoder, scan according to the marketplace's threat model, and make publication transactional so a database row cannot point at a missing derivative. The promo generator should receive only `derivative_key`; giving it `quarantine_key` defeats the capability boundary.

There is a format trade-off. Converting every accepted image to JPEG flattens transparency and uses lossy compression. If transparent product cutouts matter, define a separate PNG or WebP derivative policy and test it with the same metadata assertions. Do not quietly preserve source encoder settings, embedded profiles, comments, or application markers merely to avoid a visual-policy decision.

## Proving the boundary holds

A happy-path unit test is inadequate. Build a small corpus containing JPEG files with and without GPS EXIF, rotated images that depend on orientation metadata, transparent PNGs, malformed headers, oversized pixel dimensions, and ordinary files renamed with an image extension. The corpus does not need real coordinates; synthetic values prevent fixtures from becoming privacy liabilities.

Test denial too.

Then assert outcomes at storage. Decode the published derivative again and check that it has no EXIF entries, verify its dimensions and orientation, and ensure the video worker's identity is denied access to quarantine storage. Test duplicate delivery too: two executions for one digest should not create two independently governed originals or publish an unsanitized fallback.

Observability should count decisions without copying sensitive input. Useful signals include validation failures by reason code, decoder warnings, derivative-write latency, quarantine deletion lag, and unauthorized attempts to read originals. Alert on a rising failure ratio, but keep filenames, prompts, raw tags, and coordinates out of metric labels. High-cardinality telemetry is expensive; location-bearing telemetry is worse.

A deployment canary should exercise the actual decoder build with the corpus before traffic shifts. Decoder behavior and supported formats are runtime dependencies, so the image library version and policy version belong in the audit record. This gives responders a concrete question: which policy processed this digest?

## The rejected option still has a place

On-demand stripping was rejected for the marketplace publication path because it lets the sensitive original cross more service and queue boundaries. It can still be correct for a private evidence vault, a medical archive, or another system whose authorized users require the exact original bytes and where derived views are created inside an isolated session. In that design, access control, retention, and auditability carry the weight that early destruction carries here.

Selective tag deletion also has a valid use case when a preservation requirement demands the original encoding structure and the organization maintains a format-specific metadata policy. That is specialist work. EXIF is only one metadata family, and the C2PA specification defines provenance data that may be intentionally attached to an asset. A marketplace should decide separately whether provenance credentials are retained, validated, or omitted from a public derivative; treating every non-pixel field as interchangeable loses that distinction.

For prompt-generated promo videos, the durable rule remains direct: sanitize once before an image becomes renderable, minimize access to the original, and audit from quarantine only under explicit authorization. Downstream media jobs then inherit a clean capability instead of a recurring privacy obligation.
